# GUARD-386: риски и проверка

## Требование

Общие подключения GitHub/GitLab на уровне Harness, выбор ключа привязкой к workspace или папке. Не менять Guard/B3, статусы, договоры или платёжные процессы. Роли: владелец настраивает подключения; сессии пользуются выбранным подключением. Секреты не должны становиться артефактами рабочих пространств.

## Предварительная проверка архитектуры

Независимый анализ выявил критический риск использования workspace-selected credentials в существующем forge provider. Общий cache и watch registry адресуются `forge:host/owner/name#number`; provider получает refs без контекста сессии. Данные private PR и mergeReady зависят от аккаунта. Решение: отдельный workain bundle с явным выбором подключения на каждую операцию; общий официальный forge не менять и не подключать к новым ключам без отдельного изменения адресации cache.

Один credentials grant вместо раздельных settings/token records предотвращает рассогласование удаления, повторного создания подключения и ротации токена. Локальный credentials store не зашифрован; это не secret vault с изоляцией от остальных плагинов. Токены вводятся в owner-only settings UI, не в переписке и не через инструменты.

## Остаточные риски

- Привязка выбирает аккаунт, но не ограничивает репозитории внутри его прав; минимальные scopes обязательны.
- Работающая версия DSH — rc.1, workain master содержит более новые изменения. Плагин собран отдельно с pinned rc.1 credentials dependency; подмена runtime не нужна.
- REST-запись после timeout может уже выполниться. Автоповторов нет; нужно проверить сервис.
- Внешняя папка worktree не является дочерней папкой исходного репозитория и не должна наследовать ключ неявно.
- Нет полного кросспроцессного запрета на смену привязки одновременно с уже отправленным сетевым запросом. Запрос использует снимок ключа на момент разрешения.

## Упрощение интерфейса 10.11.2026

По замечанию владельца две самостоятельные формы заменены одной редактируемой таблицей: название, тип, скрытый ключ и список workspace. Перед изменением отмечены риски: не подменить секрет идентификатором подключения, не показывать сохранённый токен, не потерять старые folder bindings. Добавление — новая строка, workspace — флажки в последней ячейке; адрес сервера свёрнут в колонке типа. Backend-привязки папок сохраняются без изменений. Сохранение строки и нескольких workspace состоит из отдельных операций; при ошибке пользователь должен обновить таблицу и проверить частичный результат.

Проверено в текущем GUI после установки 0.1.4: ровно одна таблица, четыре заголовка Name/Type/Key/Workspaces, нет отдельных form; добавление черновика, password input, выбор workspace и отмена без записи. При viewport 1280 и 600 внешний контейнер не переполняется (scrollWidth=clientWidth); на узком экране таблица имеет собственную горизонтальную прокрутку. `npm test` 18/18, syntax check и сборка прошли. Сохранение реального ключа в браузере не выполнялось.

Mounted React/jsdom regression test now covers preservation of another row's dirty name/key/workspaces, clean-row reconciliation after reload and workspace transfer confirmation. Full test count is 18/18. Visual light/dark acceptance was not performed; live DOM smoke covered headers, no forms, draft row, password input and 1280/600 layout.

Повторное независимое ревью обнаружило сброс черновиков других строк из-за общего revision в React key; исправлено стабильными ключами строк, успех сбрасывает только сохранённую строку. Для частичного сбоя добавлено readback без повтора записи и явное предупреждение о возможном частичном сохранении. Черновики остальных строк не сбрасываются при успешном сохранении соседней строки.
